配置验证与 CI

将配置验证、产物生成和运行时检查分成三个步骤。--strict 影响退出状态，不会把所有生成步骤变成无副作用事务。

纯校验​

在配置工程目录执行，工具路径替换为实际位置：

dotnet /absolute/path/Luban.dll --conf luban.conf -t all -f --strict --errorFormat json

没有 -c 或 -d，-f 强制加载并校验数据，不写出生成文件。--strict 在有规则校验失败时返回 1。解析异常也失败。

若使用 text，增加 -x l10n.provider=default、l10n.textFile.path、l10n.textFile.keyFieldName；路径建议绝对路径，JSON 数组保留 *@。若使用 path，设置 pathValidator.rootDir。缺少这些配置时，相应检查可能未启用。

生成与运行时检查​

  1. 纯校验成功后，在本次构建的独立目录生成代码和数据。
  2. 编译/加载生成代码，断言一条主键、一个引用以及关键边界值。
  3. 验证预期 target、tag、variant 后再把同一份产物交给发布流程。

示例仓库提供：

python scripts/run.py all
python scripts/run.py dotnet
python scripts/run.py node

每项使用隔离输出；fail 样例要求非零退出及相应错误标识，不能把 fail 数据混入正常配置后忽略退出码。

自动化注意​

  • 一次运行多个输出目标时，为每个目标设置独立目录。
  • 主 CLI JSON 诊断在 stderr，日志可能在 stdout；脚本首先检查进程退出码。
  • 当前某些规则只提供通用 error.cli.validation_fail JSON，具体规则信息仍需查看日志；不要承诺所有错误都有完整单元格定位。
  • Agent stdout 是单一 JSON 结果，退出码分类与主 CLI 不同，见 Agent。
  • watch 模式用于交互开发，不用作一次性 CI 验证入口。

规则写法见校验器，按症状排错见故障排查。
